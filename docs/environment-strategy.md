# Environment Strategy

This document defines how the team provisions, deploys to, and manages environments. The strategy is selected during `/initiate` based on what's available — the team adapts to what exists rather than requiring a specific setup.

## Three Options

| Strategy | When to Use | What You Need | Multi-Dev Support |
|---|---|---|---|
| **Local** | No cloud accounts, early development, training, solo developer | Docker, machine with 8GB+ RAM | Each dev runs their own stack |
| **Cloud** | Production-bound work, team with cloud accounts | AWS/Azure/GCP account, IAM access, CI/CD platform | Ephemeral per-branch + shared test/staging/prod |
| **Hybrid** | Cloud accounts pending, or local dev preferred with shared upper environments | Docker locally + cloud for test/staging/prod | Local dev per-person, cloud for shared validation |

SM selects the strategy during `/initiate` based on what the User has available. The strategy can evolve — start local, graduate to hybrid, then full cloud as accounts and access materialize.

## Strategy 1: Local (Developer Machine)

Zero cloud dependency. Everything runs on the developer's machine via containers.

### Architecture

```
Developer Machine
├── Application (Docker container)
├── Database (Docker container — PostgreSQL/MySQL/etc.)
├── Message Broker (Docker container — if event-driven)
├── Test Runner (native or containerized)
└── Monitoring (container — Grafana/Prometheus for local observability)
```

### Implementation

```yaml
# docker-compose.yml (generated by Dmitri during first feature)
services:
  app:
    build: .
    ports: ["8080:8080"]
    environment:
      - DB_HOST=db
      - EVENT_BROKER=broker
    depends_on: [db, broker]
  
  db:
    image: postgres:16
    ports: ["5432:5432"]
    environment:
      - POSTGRES_DB=app
      - POSTGRES_USER=dev
      - POSTGRES_PASSWORD=dev
    volumes:
      - pgdata:/var/lib/postgresql/data
  
  broker:
    image: rabbitmq:3-management  # or localstack for EventBridge
    ports: ["5672:5672", "15672:15672"]

  monitoring:
    image: grafana/grafana
    ports: ["3000:3000"]

volumes:
  pgdata:
```

### How Multi-Dev Works Locally

Each developer runs their own isolated stack:
- No port conflicts (each dev uses their own Docker network)
- No shared state (each has their own database)
- No coordination needed for dev environment
- Tests run against their own local stack

```
Dev A's machine: localhost:8080 → their feature
Dev B's machine: localhost:8080 → their feature
(No conflicts — completely isolated)
```

### Environment Mapping (Local)

| Logical Environment | Local Implementation | Purpose |
|---|---|---|
| **dev** | `docker-compose up` | Run and manually verify |
| **test** | `docker-compose -f docker-compose.test.yml up` + test suite | Full automated validation |
| **staging** | N/A (or same as test with prod-like data volume) | Performance baseline |
| **prod** | N/A — graduate to cloud or hybrid when ready | Not available locally |

### Quality Gates Still Apply

Even locally, all gates are enforced:
- Traceability: 100% (verified by script against local files)
- Coverage: 100% (test runner reports)
- All tests green (BDD + unit + integration against local containers)
- NFR tests run against local stack (thresholds adjusted for dev hardware)

### Limitations

- No production deployment (obviously)
- No multi-environment promotion (dev → test only)
- Performance baselines are machine-specific (not comparable across devs)
- No blue/green deployment simulation (can do rolling restart)
- No shared staging for integration testing across features

### When to Graduate

Move to hybrid or cloud when:
- Cloud accounts are provisioned
- Features need to reach real users
- Integration testing needs real external dependencies
- Performance testing needs production-like infrastructure
- The team needs shared staging for cross-feature validation

## Strategy 2: Cloud (Full — AWS Default)

Production-bound work with full environment progression.

### Architecture

```
GitHub Actions (CI/CD)
  ├── Build + Test (every push)
  ├── Deploy to ephemeral dev (per branch, auto-created)
  ├── Deploy to test (on PR merge to main, or manual trigger)
  ├── Deploy to staging (after test validation + User approval)
  └── Deploy to prod (after staging validation + User approval)
```

### Ephemeral Dev Environments (Per Branch)

Each feature branch gets its own isolated environment:

```
feature/user-onboarding     → dev-user-onboarding.app.example.com
feature/payment-processing  → dev-payment-processing.app.example.com
feature/notifications       → dev-notifications.app.example.com
```

Created automatically on first push. Destroyed on branch delete/merge.

**Cost:** ~$3-8/day per active branch (Fargate nano + RDS micro + EventBridge)

### Shared Environments (Concurrency Managed)

```yaml
# GitHub Actions concurrency group
deploy-test:
  concurrency:
    group: deploy-test
    cancel-in-progress: false  # Queue, don't cancel
```

One deployment at a time to test/staging/prod. Others queue behind.

### AWS Resources Required

| Resource | Purpose | Access Needed |
|---|---|---|
| AWS Account | Host everything | Account ID, region |
| IAM Role (CI/CD) | GitHub Actions assumes for deploy | OIDC federation or access keys |
| IAM Role (Dev) | Developers for debugging/logs | Console access, read-only prod |
| VPC | Network isolation | Pre-existing or team creates |
| ECR | Container registry | Push from CI, pull from ECS |
| ECS/Fargate | Compute | Task definitions, service config |
| RDS | Database | Subnet group, security group |
| EventBridge | Events | Rules, targets |
| Secrets Manager | Secrets | Read from ECS tasks |
| Route53 | DNS (ephemeral envs) | Hosted zone access |
| ACM | TLS certificates | Certificate for *.app.example.com |
| S3 | CDK state, artifacts | Bucket creation |
| CloudWatch | Monitoring | Log groups, dashboards, alarms |

### What `/initiate` Needs to Capture for Cloud

```
□ AWS Account ID
□ Region (default: us-east-1)
□ VPC (existing ID or create new?)
□ IAM: How does CI/CD authenticate? (OIDC recommended)
□ IAM: What permissions does the team have?
□ DNS: Domain for environments (*.app.example.com)
□ Secrets: How are they managed? (Secrets Manager, Parameter Store)
□ Existing infrastructure: Anything we must integrate with?
□ Budget constraints: Cost limits per environment?
```

## Strategy 3: Hybrid (Local Dev + Cloud Upper)

Best of both worlds — fast local development, real cloud for validation.

### Architecture

```
Developer Machine (local)
├── docker-compose for dev/test
└── Fast iteration, no cloud latency

GitHub Actions (CI/CD)
├── Build + test on push (cloud runners)
├── Deploy to shared test (after PR passes)
├── Deploy to staging (User approval)
└── Deploy to prod (User approval)
```

### How It Works

| Stage | Where | Trigger |
|---|---|---|
| Development + unit tests | Local (Docker) | Developer runs manually |
| Integration tests | Local (Docker) + CI (cloud) | Push triggers CI |
| Test environment | Cloud (shared) | PR to main |
| Staging | Cloud (shared) | After test validation |
| Production | Cloud (shared) | After staging validation |

### Advantages

- Developers iterate fast locally (no cloud deploy latency)
- No cloud cost during development (only on push/merge)
- Shared test/staging catches integration issues between features
- Production path is fully automated and gated
- Can start with just Docker and add cloud environments incrementally

### What's Needed

- Docker (every developer)
- Cloud account (one shared, for test/staging/prod only)
- CI/CD platform (GitHub Actions, ADO, etc.)
- Fewer cloud resources than full cloud (no ephemeral per-branch environments)

## Multi-Developer Operating Model

Regardless of strategy, the team operates with:

### Branch Strategy

```
main (protected)
  ├── feature/<slug>     — Dev A's feature (isolated branch)
  ├── feature/<slug>     — Dev B's feature (isolated branch)
  ├── fix/<slug>         — Dev C's defect fix (isolated branch)
  └── refactor/<slug>    — Dev D's refactoring (isolated branch)
```

### Shared State (Lives on Main)

These files are team-wide and managed by the human SM:

```
docs/
  definition-of-ready.md     — Team agreement (changed via team consensus)
  definition-of-done.md      — Team agreement (changed via team consensus)
  sdlc-defaults.md           — Accelerator defaults (rarely changed)
  engagement/                — Engagement context (human SM + team maintain)
backlog/
  backlog.md                 — Priority order (human SM owns)
```

Developers read these from main at branch creation. If they change on main during a feature branch's life, the developer rebases to pick up changes.

### Per-Developer State (Lives on Feature Branch)

```
backlog/
  active/<their-feature>/    — Their feature's work artifacts
    feature.md               — Scenarios
    design.md                — Technical design
    traceability.md          — Their feature's trace matrix
    status.md                — Progress
src/                         — Their code changes
```

### Coordination Points

| What | Who Coordinates | How |
|---|---|---|
| Backlog priority | Human SM | Updates `backlog/backlog.md` on main |
| Feature assignment | Human SM | Standup/planning — tells each dev what to work on |
| DoR/DoD changes | Team (consensus) | PR to main modifying the docs |
| Environment access | CI/CD pipeline | Concurrency groups / queue |
| Integration conflicts | Git merge | Standard PR process — CI catches conflicts |
| Cross-feature dependencies | Human SM | Flags during planning, coordinates sequence |

### Each Developer's AI Team

Each developer has their OWN AI team instance (SM/Igor/Paul/Dmitri) that:
- Operates within their feature branch
- Reads shared state from main (DoR, DoD, engagement context)
- Writes only to their feature's workspace (`backlog/active/<their-slug>/`)
- Enforces quality gates independently
- Does NOT coordinate with other developers' AI teams

The human SM handles cross-developer coordination. The AI SM handles within-feature orchestration.

## First-Feature Pipeline Bootstrap

When `/initiate` detects no CI/CD pipeline exists, the first feature's workflow includes pipeline creation:

```
First feature only:
  /design → includes pipeline design (alongside feature design)
  /test-and-develop → Dmitri builds pipeline alongside feature
  /deploy-and-validate → first run creates the environments

Subsequent features:
  Pipeline already exists — just use it
```

### What Gets Built (Per Strategy)

| Strategy | Pipeline Deliverable |
|---|---|
| Local | `docker-compose.yml`, `docker-compose.test.yml`, `Makefile` with targets (build, test, run, clean) |
| Cloud | GitHub Actions workflows, CDK stacks, deploy scripts |
| Hybrid | Docker Compose (local) + GitHub Actions (cloud) + CDK (upper envs only) |

## Strategy Selection (During /initiate)

SM asks:

```
"Let's talk about where code will run. Quick questions:

1. Do you have a cloud account (AWS/Azure/GCP) with deploy permissions?
   → Yes: Cloud or Hybrid possible
   → No / pending: Local for now, can graduate later

2. Do you have a CI/CD platform set up (GitHub Actions, ADO Pipelines, Jenkins)?
   → Yes: Pipeline exists (or can be extended)
   → No: Team will bootstrap one

3. Do you need to deploy to production as part of this engagement?
   → Yes: Cloud or Hybrid required eventually
   → No (POC/prototype): Local is fine

4. How many developers will work simultaneously?
   → 1: Any strategy works
   → 2+: Need isolation (ephemeral or local, not shared dev)

Based on answers, SM recommends a strategy and documents it."
```

## Graduating Between Strategies

The team can move between strategies without rework:

```
Local → Hybrid:
  - Keep docker-compose (still used for local dev)
  - Add GitHub Actions workflows
  - Add CDK for cloud environments
  - Pipeline triggers on push to main

Hybrid → Full Cloud:
  - Add CDK for ephemeral per-branch environments
  - Add Route53 wildcard DNS
  - Add GitHub Actions workflow for branch-create trigger
  - Local docker-compose remains (optional fast iteration)

Any → Any:
  - Quality gates don't change
  - Test suites don't change
  - Application code doesn't change
  - Only infrastructure and pipeline config differs
```

The key: application code and tests are strategy-agnostic. Only the deployment layer changes.
